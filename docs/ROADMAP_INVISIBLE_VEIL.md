# ROADMAP: Поэтапное внедрение архитектуры «Невидимая вуаль»

Данный документ описывает пошаговый план внедрения многоуровневой системы защиты и распределения нагрузки для Sirin VPN (25–30 клиентов).

---

*Цель: закрыть критические слепые зоны без риска деградации сервиса и без масштабных переделок кодовой базы.*

- [x] **1. Расширение пула маскировочных SNI (с 4 до 8–10 доменов):**
  - Добавить доверенные домены глобальных экосистем с TLS 1.3:
    - Microsoft: `www.microsoft.com`, `dl.delivery.mp.microsoft.com`
    - Apple: `swcdn.apple.com`
    - Samsung: `www.samsung.com`

- [x] **2. Мониторинг доступности из РФ с Telegram-оповещением:**
  - Создать production-скрипт `scripts/monitor_availability.sh`.

  - Автоматическая отправка структурированного алерта в Telegram администратору с последующим подтверждением восстановления (Recovery).

- [x] **3. Архитектурное разделение плоскостей API и VPN:**
  - Размежевать IP-адрес VPN-ноды (`94.183.159.114`) и домен API управления (`crp.guseynovia.ru`).
  - Проксировать HTTP API через независимый эдж/Cloudflare или выделить независимый недорогой micro-VPS под Control Plane.
  - Обеспечить непрерывность получения клиентами обновлений `/v1/params` даже при блокировке транспортного IP.

## Фаза B: Каскадирование и партиционирование клиентов (План реализации)
*Цель: ликвидировать аномалию концентрации 30 клиентов на одном зарубежном хосте и перевести входящий клиентский трафик в статус локального внутрироссийского (ТСПУ не видит трансграничных сессий).*

> **Статус:** **Probe-нода: развёрнута (185.182.65.219). Relay 1 — кандидат.**  
> **RU VPS 1 (185.182.65.219, Москва, 1 vCPU/1GB):** probe-нода + кандидат на Relay 1. AS `AS33842`, провайдер `Citytelecom LLC` (Vector).  
> **Сетевые замеры до NL-выхода (94.183.159.114):** ping RTT min/avg/max = 37.9 / 40.5 / 46.2 мс, потери 5%; iperf3 сервер на NL-узле закрыт по соображениям OpSec.  
> См. подробности в [PROBE_NODE.md](PROBE_NODE.md).

> **Оценка ресурсов:** Срок внедрения — **3–5 дней**, операционные затраты — **~1 200 ₽/мес.**

### 1. Архитектура входного каскада (3 RU Relay + Probe)

```
[ Клиенты Группа A (8-10) ] ──> [ RU Relay 1: RU VPS 1 (AS33842) / Timeweb ] ──┐
[ Клиенты Группа B (8-10) ] ──> [ RU Relay 2: VDSina  (AS35807)            ] ──┼──> [ EU Egress: NL / BG (Xray Core) ] ──> Internet
[ Клиенты Группа C (8-10) ] ──> [ RU Relay 3: Selectel(AS49505)            ] ──┘
                                                ▲
[ Probe-нода РФ (185.182.65.219, AS33842) ] ───┴── (мониторинг TCP/TLS 443 + API /health + Telegram Alert)
```

| Узел | Хостинг / Локация | AS / Сеть | Конфигурация | Статус / Назначение |
|---|---|---|---|---|
| **RU Probe / Relay 1** | **Citytelecom / Vector** (Москва) | AS33842 (`185.182.65.219`) | 1 vCPU, 1 GB RAM, NVMe | **Развёрнут (Probe)**; кандидат на Relay 1 |
| **RU Relay 2** | **VDSina** (Москва, DataPro) | AS35807 | 1 vCPU, 1 GB RAM, 30 GB NVMe, 1 Гбит/с | Планируется (Входной узел для группы B) |
| **RU Relay 3** | **Selectel** (Москва, Берзарина) | AS49505 | 1 vCPU, 1 GB RAM, 10 GB NVMe, 100 Мбит/с | Планируется (Входной узел для группы C) |
| **ИТОГО** | **3–4 независимых AS** | — | — | Полная изоляция от блокировки одной AS |

### 2. Шаги развёртывания каскада

- [x] **Шаг 2.0. Ввод первой RU ноды (185.182.65.219):**
  - Развёрнута сторожевая probe-нода для синтетического контроля VPN и API из РФ.
  - Установлен и подготовлен `nginx-full` (`--with-stream`) для последующего stream-forward (TLS passthrough).
  - Настроен базовый hardening: доступ по SSH-ключам, `ufw`, `fail2ban`, `unattended-upgrades`.

- [ ] **Шаг 2.1. Инициализация серверов релеев:**
  - Базовая настройка Ubuntu 24.04 LTS, отключение IPv6 на внешних интерфейсах для предотвращения утечек маршрутизации, включение BBR (`net.core.default_qdisc=fq`, `net.ipv4.tcp_congestion_control=bbr`).
  - Установка легковесного Xray Core без локального хранения логов доступа (`access: "none"`).

- [ ] **Шаг 2.2. Межсерверные транспортные каскады (RU Ingress → EU Egress):**
  - Создание внутренних туннелей `mTLS stream-forward` (или WireGuard point-to-point) между каждым RU релеем и европейским сервером выгрузки (Нидерланды `sirin-main`).
  - Проброс трафика VLESS Reality без расшифровки пользовательской криптографии на уровне RU VPS: релей выполняет роль прозрачного TCP/UDP проксирования до центрального ядра, исключая возможность перехвата ключей на российских нодах.

- [ ] **Шаг 2.3. Скрипт мониторинга Probe-ноды (`scripts/monitor_availability.sh`):**
  - Probe-нода размещается в РФ и раз в 60 секунд проверяет:
    1. TLS Handshake к каждому из 3 RU релеев по их реальным портам 443.
    2. Прохождение тестового HTTP GET-запроса через туннель до контрольной точки.
  - При обнаружении 3 последовательных неудач — отправка срочного алерта в Telegram-чат администратора с кнопкой оперативного переключения трафика группы на резервный релей.

- [ ] **Шаг 2.4. Партиционирование клиентской базы в `sirinbot` и `sirinapi`:**
  - Расширение структуры `Client` в `/etc/sirin/clients.json`:
    ```json
    {
      "uuid": "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx",
      "name": "Иван Иванов",
      "relay_id": "ru-relay-1",
      "created_at": 1729548000
    }
    ```
  - **Автоматический балансировщик (Round-Robin):** при создании нового ключа бот автоматически назначает наименее загруженный `relay_id` (баланс: до 8–10 активных клиентов на один IP).
  - **Эндпоинт `/v1/params`:** по переданному UUID определяет закреплённый `relay_id` и отдаёт клиенту IP-адрес соответствующего входного релея.
  - **Управление в боте:** в карточке клиента выводится закреплённый релей (`📡 Релей: #1 (Timeweb SPB)`) и кнопка ручного трансфера: `[🔄 Сменить узел]`.
