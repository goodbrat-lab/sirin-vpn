Данный документ описывает пошаговый план внедрения многоуровневой системы защиты и распределения нагрузки для Sirin VPN (25–30 клиентов).

## Фаза B: Каскадирование и партиционирование клиентов (План реализации)
*Цель: ликвидировать аномалию концентрации 30 клиентов на одном зарубежном хосте и перевести входящий клиентский трафик в статус локального внутрироссийского (ТСПУ не видит трансграничных сессий).*

> **Статус:** **Relay 1: VLESS+XHTTP passthrough (185.182.65.219, Москва); Relay 2: VLESS+XHTTP passthrough (45.38.228.142, Германия); Watchdog multi-path мониторинг + динамический degraded fallback в Sirin API активны.**  
> **RU VPS 1 (185.182.65.219, Москва, 1 vCPU/1GB):** probe-нода + активный Relay 1 (Nginx TLS stream-forward 443 + 8443 → NL). AS `AS33842`, провайдер `Citytelecom LLC` (Vector).  
> **EU VPS 2 (45.38.228.142, Германия, 1 vCPU/1GB):** активный Relay 2 (Nginx TLS stream-forward 9443 + 9444 → NL) + watchdog probe до NL (RTT 16 мс) и Москвы (RTT 52 мс).  
> **Сетевая диагностика канала до NL-выхода (94.183.159.114):** 300 пакетов ICMP — потери **0.0%**, RTT avg **38.9 мс**, джиттер **~1.1 мс**.  
> **Многопутевой мониторинг (Watchdog):** все 3 узла кластера непрерывно шлют телеметрию в `/v1/admin/monitor`. При RTT > 150 мс или Loss > 5% узел автоматически признаётся `degraded`, и `/v1/params` мгновенно отдаёт клиентам здоровый маршрут без изменения базы `clients.json`.  
> **Живой тест Router v1.3.1:** подтверждён сквозной проход VLESS (:443) и XHTTP (:8443) с выходом `ip.me = NL`.  
> См. подробности в [PROBE_NODE.md](PROBE_NODE.md), [RELAY_1.md](RELAY_1.md), [RELAY_2.md](RELAY_2.md) и [MONITORING.md](MONITORING.md).

> **Оценка ресурсов:** Срок внедрения — **3–5 дней**, операционные затраты — **~1 200 ₽/мес.**

### 1. Архитектура входного каскада (3 RU Relay + Probe)

```
[ Клиенты Группа A (8-10) ] ──> [ RU Relay 1: RU VPS 1 (AS33842:443)      ] ──┐ (Nginx TLS passthrough)
[ Клиенты Группа B (8-10) ] ──> [ RU Relay 2: VDSina  (AS35807)            ] ──┼──> [ EU Egress: NL / BG (Xray Core:443) ] ──> Internet
[ Клиенты Группа C (8-10) ] ──> [ RU Relay 3: Selectel(AS49505)            ] ──┘
                                                ▲
[ Probe-нода РФ (185.182.65.219, AS33842) ] ───┴── (мониторинг TCP/TLS 443 + API /health + Telegram Alert)
```

| Узел | Хостинг / Локация | AS / Сеть | Конфигурация | Статус / Назначение |
|---|---|---|---|---|
| **RU Probe / Relay 1** | **Citytelecom / Vector** (Москва) | AS33842 (`185.182.65.219`) | 1 vCPU, 1 GB RAM, NVMe | **Развёрнут (Probe + Relay 1)**; готов к приёму трафика |
| **RU Relay 2** | **VDSina** (Москва, DataPro) | AS35807 | 1 vCPU, 1 GB RAM, 30 GB NVMe, 1 Гбит/с | Планируется (Входной узел для группы B) |
| **RU Relay 3** | **Selectel** (Москва, Берзарина) | AS49505 | 1 vCPU, 1 GB RAM, 10 GB NVMe, 100 Мбит/с | Планируется (Входной узел для группы C) |
| **ИТОГО** | **3–4 независимых AS** | — | — | Полная изоляция от блокировки одной AS |

### 2. Шаги развёртывания каскада

- [x] **Шаг 2.0. Ввод первой RU ноды (185.182.65.219) и запуск Relay 1:**
  - Развёрнута сторожевая probe-нода для синтетического контроля VPN и API из РФ (`scripts/monitor_availability.sh`).
  - Проведена углубленная диагностика канала (300 пакетов ICMP ping: 0% потерь, RTT 38.9 мс, джиттер 1.1 мс, MTR 100 циклов).
  - Настроен и запущен `nginx` (`libnginx-mod-stream`) в режиме прозрачного TLS stream passthrough для VLESS (`0.0.0.0:443 -> 94.183.159.114:443`) и XHTTP (`0.0.0.0:8443 -> 94.183.159.114:8443`) без расшифровки трафика и без хранения ключей.
  - Настроен базовый hardening: доступ по SSH-ключам, `ufw` (22/tcp, 443/tcp, 8443/tcp), `fail2ban`, `unattended-upgrades`.
  - Проведён живой тест Router v1.3.1 E2E через Relay 1: `ip.me = NL (94.183.159.114)`, сокеты `:443` и `:8443` ESTABLISHED к RU VPS.
  - См. спецификацию в [RELAY_1.md](RELAY_1.md).

- [ ] **Шаг 2.1. Инициализация серверов релеев:**
  - Базовая настройка Ubuntu 24.04 LTS, отключение IPv6 на внешних интерфейсах для предотвращения утечек маршрутизации, включение BBR (`net.core.default_qdisc=fq`, `net.ipv4.tcp_congestion_control=bbr`).
  - Установка легковесного Xray Core без локального хранения логов доступа (`access: "none"`).

- [ ] **Шаг 2.2. Межсерверные транспортные каскады (RU Ingress → EU Egress):**
  - Создание внутренних туннелей `mTLS stream-forward` (или WireGuard point-to-point) между каждым RU релеем и европейским сервером выгрузки (Нидерланды `sirin-main`).
  - Проброс трафика VLESS Reality без расшифровки пользовательской криптографии на уровне RU VPS: релей выполняет роль прозрачного TCP/UDP проксирования до центрального ядра, исключая возможность перехвата ключей на российских нодах.

- [ ] **Шаг 2.3. Скрипт мониторинга Probe-ноды (`scripts/monitor_availability.sh`):**
  - Probe-нода размещается в РФ и раз в 60 секунд проверяет:
    1. TLS Handshake к каждому из 3 RU релеев по их реальным портам 443.
    2. Прохождение тестового HTTP GET-запроса через туннель до контрольной точки.
  - При обнаружении 3 последовательных неудач — отправка срочного алерта в Telegram-чат администратора с кнопкой оперативного переключения трафика группы на резервный релей.

- [x] **Шаг 2.4. Партиционирование клиентской базы в `sirinbot` и `sirinapi`:**
  - Расширение структуры `Client` в `/etc/sirin/clients.json`: добавлено поле `relay_id` (0 = прямой NL, 1 = Relay 1 RU).
  - **Эндпоинт `/v1/params` (`sirinapi`):** для клиентов с `relay_id == 1` подставляет хост Relay 1 (`185.182.65.219`), для 0 — прямой NL хост.
  - **Управление в боте (`sirinbot`):** карточка клиента отображает текущий узел (`📡 Узел: Relay 1` / `🌐 Прямой NL`) с кнопкой переключения, добавлены команды `/setrelay <name|uuid> <0|1>` и `/newkey <name> [days] [relay_id]`.
