## 3. Архитектура и настройка Relay 1 (TLS Passthrough)

### 3.1. Принцип работы (Zero-Decryption / Zero-Knowledge)
Входной релей **не расшифровывает** пользовательские соединения. Используется чистый TCP stream proxy поверх `nginx` (`libnginx-mod-stream`):
1. Клиент подключается к российскому IP `185.182.65.219:443`.
2. ТСПУ видит обычную зашифрованную TLS-сессию к российскому серверу с доверенным SNI (например, `sun8-21.userapi.com` или `wildberries.ru`). Трансграничной аномалии для ТСПУ нет.
3. Nginx пересылает «сырые» зашифрованные TCP-пакеты на зарубежный сервер выгрузки `94.183.159.114:443`.
4. Рукопожатие VLESS Reality и расшифровка происходят исключительно на целевом нидерландском сервере.

```
[ Клиент Sirin ]
       │
       ▼ (Внутрироссийский TLS 443, SNI: userapi.com / wildberries.ru)
[ RU Relay 1: 185.182.65.219:443 ]
       │  (Nginx stream proxy_pass без расшифровки)
       ▼ (Трансграничный TCP forward)
[ NL Egress: 94.183.159.114:443 ]
       │  (Терминация VLESS Reality, Xray Core)
       ▼
 [ Интернет ]
```

### 3.2. Конфигурация Nginx (VLESS :443 + XHTTP :8443) и L4-оптимизация
Файл `/etc/nginx/streams-available/sirin-relay1.conf`:
```nginx
upstream sirin_nl_egress {
    server 94.183.159.114:443;
}

upstream sirin_nl_xhttp {
    server 94.183.159.114:8443;
}

server {
    listen 443;
    listen [::]:443;
    proxy_pass sirin_nl_egress;
    tcp_nodelay on;
    proxy_socket_keepalive on;
    proxy_connect_timeout 5s;
    proxy_timeout 1h;
}

server {
    listen 8443;
    listen [::]:8443;
    proxy_pass sirin_nl_xhttp;
    tcp_nodelay on;
    proxy_socket_keepalive on;
    proxy_connect_timeout 5s;
    proxy_timeout 1h;
}
```

Версия Nginx на Ubuntu 24.04: `nginx/1.24.0 (Ubuntu)` — полностью поддерживает `tcp_nodelay` в модуле stream (поддержка добавлена в 1.19.2+).

Активация в `/etc/nginx/nginx.conf`:
```nginx
stream {
    include /etc/nginx/streams-enabled/*.conf;
}
```

Симлинк и перезагрузка:
```bash
ln -s /etc/nginx/streams-available/sirin-relay1.conf /etc/nginx/streams-enabled/
nginx -t && systemctl restart nginx
```

### 3.3. Тюнинг сетевого стека TCP (BBR + FQ)
Для минимизации буферных задержек и исключения искусственного оверхеда на RU VPS активирован планировщик BBR:
```bash
modprobe tcp_bbr
echo "tcp_bbr" >> /etc/modules-load.d/bbr.conf
echo "net.core.default_qdisc=fq" >> /etc/sysctl.conf
echo "net.ipv4.tcp_congestion_control=bbr" >> /etc/sysctl.conf
sysctl -p
```
Проверка: `sysctl net.ipv4.tcp_congestion_control` возвращает `bbr`.

### 3.4. Брандмауэр (`ufw`)
Открыты порты 443 и 8443 для приёма клиентского трафика:
```bash
ufw allow 443/tcp
ufw allow 8443/tcp
ufw status verbose
```
Статус:
- `22/tcp`: ALLOW IN (SSH)
- `443/tcp`: ALLOW IN (VLESS Reality stream)
- `8443/tcp`: ALLOW IN (XHTTP stream)

Внешняя верификация: порты `443/tcp` и `8443/tcp` успешно отвечают на TCP SYN рукопожатия и ретранслируют сессии до NL-выхода (`94.183.159.114`).

### 4.4. Диагностика RTT и L4-оптимизация (Решение проблемы +108 мс)
1. **Первичная проблема:**
   При первом замере прямой пинг давал ~40 мс, а через релей — ~170 мс (+108 мс к расчетным 62 мс).
2. **Диагностика:**
   - ICMP ping RU VPS → NL VPS: `38.6 мс` (0% потерь).
   - Router WAN → RU VPS: `22.5 мс` (0% потерь).
   - Теоретический RTT через релей: `22.5 + 38.6 = 61.1 мс`.
   - Причина оверхеда: в `nginx stream` по умолчанию отключен `tcp_nodelay` (Nagle буферизовал мелкие TCP ACK и эхо-пакеты туннеля до 100–200 мс) и использовался стандартный планировщик `cubic`.
3. **Реализация фикса:**
   - В Nginx stream добавлены `tcp_nodelay on;` и `proxy_socket_keepalive on;`.
   - В ядре Linux включён планировщик BBR (`net.ipv4.tcp_congestion_control=bbr`, `net.core.default_qdisc=fq`).
4. **Итог контрольного замера:**
   - Базовый RTT сквозь туннель снизился со 170 мс до **73.8–80.8 мс** (вплотную к теоретическому пределу с учётом инкапсуляции).
   - Скорость выросла с 4.9 Мбит/с до **~20 Мбит/с**.

### 4.5. Решение о пригодности для раздачи (Инженерный вердикт)
- **Вердикт:** Relay 1 **ПОЛНОСТЬЮ ПРИГОДЕН** для эксплуатации.
- **Политика распределения:**
  - Согласно регламенту (RTT в диапазоне 70–100 мс), Relay 1 выделяется для группы клиентов (3–5 пользователей, особенно тех, у кого прямой NL замедляется ТСПУ на трансграничном стыке).
  - Клиентам со стабильным трансграничным доступом по умолчанию сохраняется прямой NL (`relay_id=0`), а при возникновении блокировок или деградации скорости они мгновенно переводятся на Relay 1 (`relay_id=1`).

### 4.6. Сохранение маршрутизации прокси
Маршрут `/32` до сервера управления (`200.10.40.239 dev pppoe-wan scope link`) полностью сохранён и остаётся неизменным.

### 4.7. Регламент отката (Fallback)

## 5. Партиционирование клиентов (`relay_id`) и управление через бота

### 5.1. Архитектура единого источника истины (`/etc/sirin/relays.json`)
Релеи описываются в общем динамическом хранилище `/etc/sirin/relays.json`:
```json
{
  "relays": [
    {
      "id": 1,
      "name": "Relay 1 (Москва, RU)",
      "host": "185.182.65.219",
      "port_vless": 443,
      "port_xhttp": 8443,
      "max_clients": 10,
      "enabled": true
    }
  ]
}
```
- `id: 0` зарезервирован для **Direct NL** (`94.183.159.114`, безлимитная емкость).
- `id: 1..N` — произвольное количество каскадных релеев.
- Эндпоинт `/v1/params` (`sirinapi`) динамически читает `relays.json`:
  - Для `relay_id == 0`: отдаёт прямой нидерландский IP/домен.
  - Для `relay_id == N`: отдаёт `host` и порты (`port_vless`, `port_xhttp`) активного релея, а также заголовок `X-Relay-Load: <текущие>/<лимит>`.
  - Если релей отключён (`enabled: false`) или не найден: срабатывает fallback на Direct NL с записью предупреждения в системный лог.

### 5.2. Полнофункциональный раздел «📡 Релеи» в Telegram-боте
1. **Главный экран релеев (`menu:relays`):**
   - Отображение всех узлов и их загрузки в реальном времени (`👥 X / Y`, остаток мест).
   - Кнопки `[👥 Клиенты]` для каждого узла.
   - Кнопка `[📋 Назначить]` для быстрой привязки клиентов.
   - Пошаговый FSM-мастер добавления новых узлов `[➕ Добавить релей]` с автогенерацией `id`.
2. **Карточка релея (`relay:view:<id>`):**
   - Управление емкостью: `[✏️ Изменить лимит]`.
   - Управление адресом: `[📡 Изменить host]`.
   - Включение/отключение: `[⛔ Отключить]` / `[▶️ Включить]`. При отключении узла с клиентами запрашивается подтверждение и происходит автоматический перевод клиентов на Direct NL с отправкой персональных уведомлений в Telegram.
   - Удаление узла: разрешено только при нулевом количестве клиентов.
3. **Карточка клиента:**
   - Кнопка `[🔄 Узел: <Текущий>]` открывает экран выбора узла с проверкой лимита мест (`max_clients`).
4. **Текстовые команды (алиасы):**
   - `/setrelay <имя|uuid> <id>` — смена узла с проверкой емкости.
   - `/newkey <имя> [дни] [relay_id]` — создание ключа сразу на целевой узел.

## 6. OpSec (Операционная безопасность)

Узел Relay 1 подчиняется строгим правилам изоляции:
1. **Никаких ключей и баз:** на RU VPS отсутствуют `clients.json`, UUID, приватные ключи Xray Reality, база данных и токены администратора.
2. **Никакой терминации криптографии:** трафик проходит сквозь Nginx в неизменном зашифрованном виде.
3. **Расходный статус:** при блокировке IP-адреса узла ТСПУ инфраструктура не страдает — клиенты моментально переключаются на прямой NL-выход или другой релей через обновление параметров в `sirinapi`.
